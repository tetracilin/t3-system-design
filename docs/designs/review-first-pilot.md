# Design: Review-first pilot of T3 Desk v1

## Problem Statement

Juniors at TECOTEC do not follow systems-engineering practice. The v2.5 workbooks (RTM, Phân rã, BOM) exist, but in
Viet's words: "Workbook exist but difficult to use and maintain. Junior engineer does not have to care and also does not
understand system engineering practice now. Template exist to help but junior failed to fill in the template correctly
and systematically."

That is two problems:

1. **Does not understand.** Guidance can fix this. v1 already has the decision tree, next action per leaf, warnings and gates.
2. **Does not have to care.** This is about incentive, and no data-entry UI fixes it. Juniors take care over what the
   reviewer judges them on.

## Demand Evidence

None yet. T3 Desk v1 is built (460+ tests against a fake Teable, verified once against the live Teable on 5 Oct 2026) and
has zero users. Viet's answer was "Nobody yet, it's a bet." The first real pilot is the experiment.

## Status Quo

The v2.5 templates exist but are filled wrongly or skipped. SE practice lives in Viet's head. There is no record of
what a review corrected.

## Target User & Narrowest Wedge

- **First user: the reviewer** (system designer / Viet). The weekly design review runs on T3 Desk.
- **Second user: one named junior on one real upcoming project.** Viet says he can name both; they are not written here
  yet (see The Assignment).
- **Wedge:** a weekly review view plus review findings that the junior sees as their own to-dos. It is the smallest build
  where the junior is judged inside the tool.

## Constraints

- CLAUDE.md stack and the 10 rules stay binding: no delete, one write path (draft → validation → Commit), schema only in
  `schema.yaml`, pure `rules.py` with trigger and no-trigger tests, Vietnamese UI text from label files.
- The pilot runs on Windows with `run.bat` against the NAS Teable. `t3desk bootstrap` must be re-run on the NAS base
  first, because `nut.ma_kt` is a new column.
- Running against the real NAS needs Viet's go-ahead (CLAUDE.md).

## Premises (agreed 2026-10-08)

1. The problem is that juniors don't follow SE practice, not data-entry speed. The value of T3 Desk is guiding and
   checking.
2. **Scope freeze:** no UI v2 (4-pane, inline grid, `ghi_chu` notes, Hermes panel, keyboard model), no Electron,
   Hyprland or Quickshell, until one named junior has used v1 on a real project with Viet watching and not helping.
3. **The reviewer is the first user:** the weekly design review runs on T3 Desk, so juniors fill it in because that is
   where they are judged.
4. **(Revised after the second opinion.)** The form warns only for order-of-work errors that cost a junior days: a spec
   drafted before gate 2, a second architecture marked `Chọn`. Errors of meaning (a vague requirement, two architectures
   that are really the same idea) go to the review. Every review correction is logged so the pilot data decides what
   else to automate.
5. The pilot is Windows + `run.bat` + NAS Teable only. macOS and Linux packaging waits.

## Cross-Model Perspective (Claude subagent, cold read)

- **Steelman:** T3 Desk passes on a senior engineer's SE judgment. It puts the method in every junior's path as one next
  action with a reason, and a check that flags work done out of order.
- **Key quote:** "Junior engineer does not have to care". Software fixes "does not understand"; only a review the junior
  is judged in fixes "does not care".
- **Challenged P4:** a junior's real mistakes are about meaning, or span several records, so form-time warnings teach
  "clear the red marks". Proposed test: tag every review correction as "rule could catch at the form" or "needed
  judgment / crossed records". Viet accepted the revision.
- **48-hour build:** a review view on Tổng quan, findings as records, a printable review, three rule fixes, and seeding
  the pilot by entering requirements together. No Excel import, because the v2.5 workbooks are not in `docs/reference/`
  (checked: only `gbrain-mcp.md` and `hermes-api-server.md`).

## Approaches Considered

- **A. Pilot v1 as it is, review on paper:** rejected as the plan, kept as the fallback. It is the fastest, but the
  review stays outside the tool.
- **C. UI v2 first, as specced in `docs/UI-V2-SPEC.md`:** rejected. It breaks P2, makes data entry faster for people who
  have no reason to enter data, and the pilot slips 4 to 6 weeks.

## Recommended Approach: B. Review mode + pilot (chosen by Viet, 2026-10-08)

### 1. Three rule fixes (`rules.py`, each with a trigger test and a no-trigger test)

| Fix | Rule | Where it shows |
| --- | --- | --- |
| a | Mandatory (`muc` = Bắt buộc) requirement with empty `tieu_chi_nghiem_thu` → soft warning | Row, Yêu cầu screen, review view |
| b | Existing rule `tree_too_early` (`rules.py:576`, REQUIREMENTS §7 "Đi sâu quá sớm"): no new rule. Show it on the form | **On the spec and candidate forms at save**, via the draft overlay `tables_for_rules` (`server.py:243`), not only on the tree screen |
| c | More than one `kien_truc` with `trang_thai` = Chọn → warning | Kiến trúc screen and the review view. Other Choose buttons say a choice already exists |

Fixes (a) and (c) add warnings that section 7 does not have. They are listed under Departures below. Fix (b) only
changes where an existing warning shows.

### 2. Weekly review view ("Rà soát tuần")

A role-default view for the System designer. It is built from the existing `/api/overview` (`server.py:684`) and the
`Analysis` object (`rules.analyse`, `warnings_for`). It adds no new rules.

- Grouped by owner (`phu_trach`), then by leaf. Each leaf shows its next action, its open warnings, and its records
  changed since the last review date. A first group **"Cấp hệ thống" (N0)** holds what has no leaf: changed
  requirements, architectures, allocation rows and their warnings.
- **"Since last review"** uses the cached `lastModifiedTime`. The last review date is a `cai_dat` row
  (`ngay_ra_soat_cuoi`), set by a "Kết thúc rà soát" button through the normal draft → Commit path. It is a new
  `cai_dat` key, so it goes in `schema.yaml` defaults and `labels_*_vi.yaml`.
- "Changed since last review" counts **committed** changes only (cached `_modified`, `server.py:115`). Drafts are not
  shown, because the review judges what was sent.
- `ngay_ra_soat_cuoi` is a UTC timestamp (ISO 8601), set when "Kết thúc rà soát" is committed, and compared with
  `lastModifiedTime`. The review cycle is a second new `cai_dat` key, `chu_ky_ra_soat_ngay` (default 7). With no
  `ngay_ra_soat_cuoi` yet, "since last review" means the last `chu_ky_ra_soat_ngay` days.
- "Kết thúc rà soát" is enabled for the System designer role only, like the gates (REQUIREMENTS §2).
- At the top: the dashboard counters (section 7) and the list of open findings.
- Read-only for everyone except the action "Ghi nhận xét" (below). Must draw within 1 s at the section 4 limits.

### 3. Review findings = `sai_lech` change cards (no schema change proposed)

`sai_lech` already has `mo_ta`, `ma_nut`, `nguoi_nhan`, `han`, `trang_thai` (Mở / Xong / Hủy). The Engineer tree already
asks "Có thẻ sai lệch giao cho bạn?" (`rules.my_change_cards`), and `task_outbox` already turns open cards into tasks.

- "Ghi nhận xét" opens a `sai_lech` draft with `ngay` = today and `han` = today + `chu_ky_ra_soat_ngay`. Findings are
  written during the meeting, before "Kết thúc rà soát" moves the last review date. The other defaults
  depend on the row it was pressed on:

  | Row kind in the review view | `ma_nut` default | `nguoi_nhan` default | `mo_ta` starts with |
  | --- | --- | --- | --- |
  | Leaf row | the leaf | the leaf's `phu_trach` | (empty) |
  | Warning row | the warning's node | the warning's owner | the warning's record code, e.g. `[TS-011]` |
  | Changed-record row | the record's node | the node's `phu_trach` | the record code |
  | Requirement or architecture (no node) | `N0` | **empty: the reviewer must pick** | the code, e.g. `[R7]` |

- `nguoi_nhan` is filled from a picker of the known `phu_trach` names, not free text. Matching is exact-string
  (`rules.py:882`), so a typo would hide the finding.
- The form has a two-option toggle **Quy tắc bắt được / Cần phán đoán**. `mo_ta` always starts in the fixed order
  `[QT|PĐ] [record code] text`, e.g. `[PĐ] [R7] Tiêu chí chưa đo được`. This is the correction log for revised P4. Count the prefixes after 4 reviews.
- The assignee (`nguoi_nhan`) marks the finding Xong when they believe it is fixed. The reviewer checks it at the next
  review and reopens it (Mở, with a note) if it is not. Only the reviewer may set Hủy.
- A finding is closed by setting `trang_thai` to Xong or Hủy. The form asks for a closing reason, which is appended to
  `mo_ta` (`-- Đóng: <lý do>`), in line with REQUIREMENTS §5 "retire with a reason". It is never deleted.
- The junior's Tổng quan does NOT show open `sai_lech` today: `/api/overview` (`server.py:695`) lists `cong_viec`
  tasks only, and those come from `sai_lech` only when `task_outbox` runs, which commit does not call yet
  (`docs/notes/flow-predator.md:29`; itself a departure from REQUIREMENTS §9.5).
  Add a "my open findings" list to `/api/overview` read straight from `sai_lech` (`nguoi_nhan` = me, `trang_thai` Mở),
  so findings show without any plugin.

### 4. Printable review page

A print stylesheet in `style.css` for the review view. One page per meeting is the meeting record. No new dependency.

### 5. Pilot setup (Viet's go-ahead needed for the NAS)

1. Re-run `t3desk bootstrap` on the pilot base (adds `nut.ma_kt` and the two new `cai_dat` keys).
2. Install on the junior's Windows PC: `run.bat --browser`.
3. Session 1: Viet and the junior enter the real project's requirements together. After that, Viet watches and does not
   help.

### Departures from REQUIREMENTS.md (add to STATUS.md)

- Fixes (a) and (c): two new warnings not in §7.
- `cai_dat` gains `ngay_ra_soat_cuoi` and `chu_ky_ra_soat_ngay`, beyond the fixed row list in §4.
- `sai_lech` is used as the review-finding record and is written by the System designer. §2 gives change cards to the
  PM (see open question 3).
- Already open, not caused by this design: commit does not call `task_outbox` (§9.5).

**Not built:** UI v2, the Hermes panel, plugin UI wiring, Excel import, node retirement, macOS and Linux packaging.

## Open Questions

1. Does `sai_lech` ("change card") read right to juniors as "review finding", or does it need its own label in
   `labels_ui_vi.yaml`? A label change is cheap; a new table is not.
2. Should requirement- and architecture-level findings attach to N0 (above), or should `sai_lech` get an optional
   `ma_ban_ghi` field? That would be a schema change, so ask before doing it.
3. Who may write findings? REQUIREMENTS §2 gives change cards (`sai_lech`) to the PM. This design has the System
   designer write them in review. Is it both roles, the System designer only, or also a senior acting as reviewer?

## Success Criteria

- The first pilot session takes place on a real project within 2 weeks of this doc being approved.
- Four weekly reviews run on T3 Desk, and each one produces findings as `sai_lech` records.
- Open findings older than one review cycle trend down by review 4.
- After 4 reviews, the `[QT]` / `[PĐ]` tally decides whether more form-time rules (P4) are worth building.
- No spec is saved before gate 2 without the warning showing on the form.
- `pytest -q` is green, the predator flow test still passes, and `scripts/smoke.py` passes.
